Recently, my homelab services were reachable from the outside in two ways, and both had a catch.
The user-facing services (Jellyfin, Vaultwarden, the portfolio homepage) had been running
directly over my home connection and a Caddy reverse proxy since the
[ingress move](/en/blog/netzwerk-upgrade). Everything else — the \*arr suite, dashboards, admin
interfaces — still hung off a **shared dedicated server** that ran Pangolin as a reverse proxy
and routed back home to me through an IPsec tunnel.

The dedicated route had an ugly symptom: from some networks — **mobile** networks above all —
connections died in timeouts, while they worked perfectly from the home network and from data
centers. The cause was on the shared server's Pangolin edge (probably IP reputation against
CGNAT ranges), and since the server isn't mine alone, I couldn't fix it.

So the plan: **a single, self-hosted edge** that replaces both Caddy _and_ the dedicated
server, with **central single sign-on** in front. Reverse proxy: Pangolin (which brings
Traefik along). Identity provider: Authentik. Pretty much the same architecture that was already
running on the dedicated server. Sounds like an afternoon. It turned into several days — and as
always, the interesting parts were the ones that weren't in the plan. As with the
[firewall audit](/en/blog/firewall-audit-zero-trust), I had an AI as my assistant at the
terminal; the real work was verifying each of its steps empirically.

## The target architecture

Two new LXC containers on the Proxmox host, both in the server VLAN:

- **Authentik** — the OIDC identity provider. One login, one user database.
- **Pangolin + Traefik** — the only reverse proxy for WAN _and_ LAN. No tunnel, no
  Newt/Gerbil layer: Pangolin's resources point directly at the internal service IPs, because
  everything is on the same network.

The data flow afterwards:

```plain
Internet → Cloudflare (wildcard *.vugas.de → home IP via DDNS)
         → OPNsense (WAN:443 → Pangolin)
         → Traefik (wildcard TLS, SSO wall)
         → Authentik (OIDC)  or directly → backend service
```

On the LAN, AdGuard rewrites all `*.vugas.de` straight to Pangolin, so home devices never take
the detour via the public IP. Three auth classes sort the services:

- **Public** — portfolio, Jellyfin, Vaultwarden, the status page: their own app login, no SSO
  wall (family and strangers don't have Authentik accounts).
- **Gated** — \*arr, SABnzbd, Paperless, Firefly, the Proxmox web UI, the OPNsense web UI and
  co.: Pangolin enforces the Authentik login in front of them.
- **Break-glass** — every service stays reachable internally via its direct IP, in case SSO is
  ever down.

So much for theory. Now to the places where reality hit back.

## Bug 1: A slash that made Postgres unreachable

Pangolin's installer ran through and pulled the containers — and the main container stubbornly
stayed `unhealthy`. Postgres was healthy, but Pangolin couldn't reach it: `ECONNREFUSED` on every
migration. Curiously, **`curl` from the same container connected to `postgres:5432` without
problems**. TCP worked, the application didn't.

The error was an `AggregateError` with _two_ bundled refusals — the signature of `localhost`
(127.0.0.1 **and** ::1). So the application wasn't even trying to reach `postgres`. A small parser
script brought it to light: the Postgres connection string generated by the installer looked
(schematically) like this:

```plain
postgresql://pangolin:/xxxxx@postgres:5432/pangolin
```

The automatically generated password **started with a slash** (the Base64 alphabet contains `/`
and `+`). In a URL, an unencoded slash ends the authority — the parser interpreted the host as
empty or fell back to a default and ended up at `localhost`. Nothing was listening on 5432 there.

Fix: percent-encode the password in the connection string (`/` → `%2F`). No need to reset
credentials, just a properly encoded string.

**Lesson 1:** When TCP works but the app reports "connection refused", the network isn't to
blame, but how the app _interprets_ the connection details. And password generators that spit
out URL special characters are a source of bugs you only want to debug once in your life.

## HTTP-01 was the wrong challenge

Traefik fetched its certificates via HTTP-01 — a separate challenge per hostname over port 80.
That's impractical when the services aren't public yet (the move was running in parallel with
the existing setup) and you want a wildcard anyway. So I switched the existing `letsencrypt`
resolver from HTTP-01 to **DNS-01 via Cloudflare** — with the same API token my Caddy was already
using for its wildcard.

The neat part: because I kept the resolver name, _all_ routers followed automatically — the
existing ones as well as those Pangolin would generate in the future. After a short test against
the staging CA (to avoid rate limits), a valid wildcard certificate for `*.vugas.de` was in place.
DNS-01 validates via a TXT record and is therefore completely independent of whether the service
is already reachable — exactly right for a move during live operation.

## The outage I caused myself

Now the unpleasant part. To make Pangolin reachable on the LAN, AdGuard needed a DNS rewrite. I
added the entry, restarted AdGuard — and **half the network lost DNS**. `:53` no longer bound.
`systemctl` reported the service as `active`, the process was there, the log ended silently after
"starting https server", and nothing was listening on port 53.

I got thoroughly lost: suspected the config YAML, checked `bind_hosts`, ruled out IPv6, searched
for port conflicts, even restored the backup and rebooted the container. Nothing helped. The
actual finding was a `journalctl | grep` away the whole time:

```plain
AdGuardHome.service: Main process exited, code=killed, status=9/KILL
AdGuardHome.service: Failed with result 'oom-kill'.
```

**Out of memory.** The AdGuard container had a 512 MB limit and was chronically running just
below it at \~508 MB. My restart triggered a filter reload spike that broke the limit — the OOM
killer struck exactly _at the DNS bind_, systemd restarted it, and the cycle repeated. A perfect
crash loop that looked as if I'd broken the configuration. But I hadn't — my edit was perfectly
fine, the timing was just unfortunate.

A one-line fix: raised the limit from 512 to 1024 MB (the host had plenty free), and DNS was back
immediately. Along the way I learned a second pitfall: rewrites added manually to AdGuard's YAML
need an explicit `enabled: true`, otherwise AdGuard normalizes them to `false` on the next start
— inactive.

**Lesson 2:** "Service active, but the port doesn't bind and the process is idle" means: **first**
`journalctl | grep -i oom` — before you spend half the night suspecting the configuration. And a
service chronically running at its RAM limit is a ticking time bomb that goes off at the next
restart, not before. This is related to the [AdGuard DNS puzzle](/en/blog/youtube-aussetzer-adguard)
from a while ago — DNS is the layer whose errors look the most innocent and cause the most
collateral damage.

## The API that officially didn't exist

For \~20 services, I didn't want to click the resources together by hand, but script them.
Pangolin has an integration API, I had a valid API key — and got a `401 Unauthorized` on _every_
authenticated endpoint. The key was right (the last characters matched the DB entry, `isRoot`,
all permissions), the format was right, the header was right.

A `grep` through the app bundle in the container produced two clues: a switch called
`enable_integration_api` and a separate `integrationApiServer`. The integration API was simply
**off by default**. After `enable_integration_api: true` and a restart, a new line appeared in
the log:

```plain
Integration API server is running on http://localhost:3003
```

The API ran on its **own port** (`:3003`) and under a different path (`/v1`, not `/api/v1`) —
and is deliberately _not_ routed to the outside through Traefik. From the inside, it was
immediately reachable via `docker exec`. After that, the rest was an assembly line: a small
script that creates a resource and a target per service and sets the auth class. Seventeen
services in one run.

**Lesson 3:** A `401` doesn't always mean "wrong key". It can also mean "the feature that serves
this endpoint isn't running at all". A look into the shipped bundle is sometimes faster than any
documentation.

## Two final OIDC traps

Once the scaffolding was in place, two classic SSO pitfalls remained:

**"The request is otherwise malformed".** Logging in via Authentik aborted with this rather
unhelpful OAuth2 message. Authentik's log was more precise: `Invalid grant_type for provider`. I
had created the OAuth2 provider via a script (ORM) and overlooked a field the web interface fills
in automatically: the allowed `grant_types`. Empty list → no `authorization_code` → "malformed".
One value set, done.

**The circular gate.** For the browser to reach Authentik at all, I made Authentik a Pangolin
resource. Except Pangolin promptly protected it with its _own_ SSO wall — which in turn needs
Authentik. A perfect circle: to log in to Authentik, you first have to log in to Authentik. The
resource that carries _the_ login must itself be public. One flag flipped, circle broken.

## The cutover

With everything wired up came the live part — deliberately in stages, with the old Caddy as an
immediate safety net:

1. **LAN first:** switched AdGuard's rewrites for the migrated hosts over to Pangolin and tested
   every service on the home network.
2. **External:** redirected the WAN port forward in OPNsense from Caddy to Pangolin — using the
   proven method from the [firewall audit](/en/blog/firewall-audit-zero-trust): edit
   `config.xml`, `configctl filter reload`, and verify in the live `pfctl` that the rule really
   applies.
3. **DNS:** And here came one more surprise. The wildcard `*.vugas.de` wasn't an A record at all,
   but a CNAME to the dedicated server. So I switched it to an A record with my home IP. Even so,
   `sonarr` & co. promptly still pointed to the old server: they had **their own, specific**
   records that overrode the wildcard. Those had to be moved one by one.

Because my home IP is dynamic, the final touch was extending the DDNS updater: besides the
individual hosts, it now also maintains the wildcard record (with `set -f`, otherwise the shell
expands the `*` as a glob — another one of those little things you see once and never forget).

Then a full test run, externally over mobile data: all services reachable, valid certificates,
clean SSO login, **no more timeouts**. Exactly the proof this was all about. To finish, I stopped
the Caddy service (the container only keeps running for DDNS) and cleaned up the dead DNS records.

## The encore: a bug that only struck the next day

I could have sworn it was done. But the day after the cutover came the message: `jelly.vugas.de`
wasn't reachable from a phone — my brother confirmed it. Everything worked from the home network,
dead from the outside. And the most confusing part: **sometimes** it worked, **sometimes** it
didn't.

DNS? Pointed correctly to the home IP. Firewall rule? Clean in the live `pfctl`, pointing to
Pangolin. Pangolin? Running, dutifully returning its `302` internally. So I dug through the
network stack — with `tcpdump` on the WAN interface while my brother and I took turns triggering
from our phones. (A small trap: a `tcpdump` started in the background via SSH dies from SIGHUP as
soon as the session closes — you have to run it in the foreground.)

The capture uncovered it layer by layer: the SYN arrived on the WAN. A SYN-ACK went back — so the
TCP handshake was answered. The MTU was clean (MSS clamped to 1452, no blackhole risk). A complete
capture then showed the real picture: **TLS handshake complete, certificate valid — and then the
browser simply doesn't send an HTTP request and closes after 10 seconds.** No reset, no error, no
log line in Traefik. A ghost.

The decisive observation was a comparison: `vugas.de` — my public homepage, which runs through its
own Traefik router *without* the SSO middleware — worked reliably. The gated services behind it
didn't, and `jelly` went "sometimes yes, sometimes no". Intermittency plus "one service works, the
other doesn't" almost always smells of **protocol racing**.

The solution to the puzzle: Traefik advertised **HTTP/3** on every response —
`Alt-Svc: h3=":443"; ma=2592000`. The browser remembers that (for 30 days!) and tries QUIC over
**UDP** 443 on the next visit. My OPNsense, however, only forwards **TCP** 443 to Pangolin, no UDP.
So every HTTP/3 attempt ran into the void; depending on the browser's mood, the connection hung in
the UDP blackhole or fell back to TCP — delayed and unreliably. Exactly the "sometimes this,
sometimes that".

The fix was one line: turn off the HTTP/3 advertisement in Traefik. No more `Alt-Svc`, everything
runs over solid h2/TCP. (If you really want HTTP/3, you'd also have to forward UDP 443.)

**Lesson 5:** "Handshake complete, but no request" is the signature of a problem *above* the TCP
layer — and `curl -k` will never tell you, because it neither speaks HTTP/3 nor checks the
certificate. A reverse proxy advertising a protocol the firewall doesn't even let through is a
subtle, nasty trap. It only became visible in the packet capture on both sides.

## Takeaways

Four things stick. First: **installers are software, and software has bugs** — a generated
password with a slash cost me an hour, even though "nothing" was misconfigured. Second: the most
dangerous outage is the one you trigger yourself while doing something harmless; the OOM kill had
nothing to do with my edit, only with its timing. Third: between "planned" and "running", a move
like this hides half a dozen undocumented little things — a disabled API, a missing field, a CNAME
instead of an A record, a glob at the wrong moment, an advertised protocol the firewall doesn't
even let through. And fourth: an AI at the terminal makes a project like this dramatically faster
— but only because I verified every finding myself instead of trusting the first green checkmark.

In the end, I have what I wanted: a single edge, one login, no dependency on someone else's
infrastructure — and mobile access that just works.
